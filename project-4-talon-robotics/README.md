`✦` **Why a green tick can describe software that no longer exists.** A verification is evidence

| Subsystem | Criticality | Must-ship | Readiness | Builds changed |

| **Flight Control Interface** | Safety | 47 | **23.40%** | **45** |
| **Payload Release Mechanism** | Safety | 62 | **32.26%** | **42** |
| Everything else (6 subsystems) | — | 172 | 59–83% | 15–23 |

The two worst subsystems are the two most-changed, and they carry **39% of everything that must
ship**. They are not behind on testing — they are still being designed.

## The modelling decision everything rests on

**A verification is a dated fact against a build, not an attribute of a requirement.**

The obvious model puts a `Verified` flag on the requirement row. It is simpler, it is what most
requirements tools do, and it makes the central question impossible to ask. So `Fact_TestRun`
carries a `BuildKey`, and `Fact_BuildSubsystemChange` records what each build touched. Staleness is
then **computable** rather than asserted:

> A verification is **current** when nothing it depended on has changed since it ran — no later
> build touched the same subsystem, and the requirement itself was not *modified*.

This is the same shape as Project 3's dated price agreements. A contracted price is true between two
dates; a test result is true for one build. Storing either as an attribute lets today's answer
silently govern yesterday's question.

**What is deliberately not a staleness rule: age.** A verification from fourteen months ago is fine
if nothing underneath it has moved; one from last Tuesday is worthless if the subsystem was
rewritten on Wednesday. Elapsed time is the proxy people reach for because it is easy to compute.

**And *clarified* is not *modified*.** Rewording a requirement for a certification reviewer does not
change the behaviour under test. Treating it as invalidated evidence would inflate the finding and
cost it credibility on the part that is real.

## Rig contention is not a second problem. It is the cause.

Approaching a release candidate the programme re-runs its regression suite, and anything re-run on
the candidate is current by definition. What does **not** get re-run is whatever needs the scarce
resource:

| Test level | Made the RC regression | Why |
|---|---:|---|
| Unit | ~90% | Automated, effectively free |
| Integration | ~88% | Automated, cheap |
| **Hardware-in-the-loop** | **~74%** | Six rigs, bookable hours |
| **Field (airframe)** | **~54%** | One airframe, weather, crew |

So stale evidence lands hardest on exactly the Safety and Regulatory requirements whose policy
*demands* hardware evidence. "Verification is behind" and "we cannot get rig time" are one item on
the risk register, not two — and the recommended action for most of the queue is **book rig time**,
not write more tests.

## 113 requirements are verified by evidence that does not count

`Ref_VerificationPolicy` states what counts as evidence, per requirement type. It is the most
contestable input in the analysis, so it lives in a table a systems engineer can argue with rather
than inside a query nobody reads.

- **110 requirements** pass only below the level their type demands — a safety behaviour signed off
  by a unit test.
- **46 requirements** (40 of them must-ship) have passing evidence produced by their own owner, against a policy requiring
  an independent witness.

Both read as a pass on every dashboard the programme currently runs. **Policy compliance: 77.45%.**

## The verification queue

226 outstanding requirements is not a plan. A programme can book about 180 rig hours a week, so the
queue stays complete for audit and marks what is actually schedulable.

**40 requirements in the first week. 610 rig hours — 3.4 rig-weeks — to clear the backlog.**

**The action follows the state, not the rank.** Sending a team to re-run a test when the
*requirement* changed risks certifying against the old wording, so that case goes to a systems
engineer first. `INDEPENDENT_WITNESS` costs a signature rather than rig time, which is why it is
worth separating instead of lumping everything into "not done".

## The Excel workbook

`excel/Talon_Readiness_Control.xlsx` — **a control, not a report.**

Nothing on the Dashboard is a pasted number, and **both sides of the headline comparison are
computed in Excel**: work-item completion with `COUNTIF` over the work-item extract, ship readiness
with `COUNTIFS` over the requirement extract. A comparison in which one side is copied from the
other tool proves nothing about either.

All **16** validation checks reconcile against SQL. Change *Rig hours per week* on the Control sheet
and the queue re-bounds itself — the "what if we add a rig" question answered without editing
anything.

**No dynamic-array formulas** — `FILTER`, `SORT` and `UNIQUE` would break the file on Excel 2019 and
LibreOffice.

## The Power BI model

`powerbi/Build_PowerBI_Model.ps1` scripts 12 tables, 9 relationships and **53 DAX measures** into a
running Desktop session through the local Analysis Services engine. `Validate_PowerBI_Model.ps1`
then queries the model **in DAX** and reconciles **28 of 28** figures against SQL.

Three of those checks go past the totals on purpose: the five verification states must partition the
population, the two stale buckets must be mutually exclusive, and readiness is reconciled for **all
eight subsystems individually**. A headline can agree while every cut beneath it is wrong — Project
3 shipped a measure that was right for the one vendor anyone checked and wrong for the other 35.

## Data quality

The gate measures the share of **must-ship requirements whose readiness rests on flagged data** —
not a count of defective rows. A defect count says how untidy the data is; it does not say whether
to trust the answer.

**It passes at 1.779% against a 2.000% tolerance.** A margin, not comfort.

Eleven behavioural checks run and **three found nothing and are reported anyway**, because a summary
listing only what was found cannot distinguish *we looked and it was clean* from *we never looked*.

**Policy breaches are deliberately excluded from the gate.** A safety requirement verified by its
own owner is accurate data recording a practice that should not have happened.

---

## Defects worth reading about

**A function that took an as-of parameter and ignored it.** `usp_ReadinessTrend` drew a flat line:
work-item completion read 93.86% at every build across twenty months of a programme that was
demonstrably closing items throughout. `fn_ReadinessKPI` accepted `@AsOfDate` and used it for every
metric except work items. A function that offers a point-in-time parameter and answers about *now*
for one output is worse than one that never offered it.

**A UAT harness that hid its own failures.** `#UATResults` is created inside the test transaction,
so `ROLLBACK` dropped it — and the failure-detail `SELECT` ran after the rollback. A failing suite
reported `Invalid object name '#UATResults'` instead of the failures. The branch only executes when
a case fails, which is exactly why a suite that had always passed would never reveal it.

**A fixture that stopped testing anything.** After the generator was tuned, UAT-06's fixture
selected nothing and the case returned `NULL` rather than failing. A fixture that depends on the
shape of the generated data is one parameter change away from testing nothing — and it fails
silently. It now creates its own build, which changes no subsystem, so the only thing that can
invalidate a verification is the rule under test.

Full write-ups in [docs/data_validation_report.md](docs/data_validation_report.md).

## Running it

```bash
sqlcmd -S <server> -E -d master        -i sql/01_create_schema.sql
sqlcmd -S <server> -E -d TalonDelivery -i sql/02_generate_synthetic_data.sql
sqlcmd -S <server> -E -d TalonDelivery -i sql/03_core_views.sql
sqlcmd -S <server> -E -d TalonDelivery -i sql/04_data_quality_checks.sql
sqlcmd -S <server> -E -d TalonDelivery -Q "EXEC dbo.usp_RunDataQualityChecks"   # the gate
sqlcmd -S <server> -E -d TalonDelivery -i sql/05_kpi_views.sql
sqlcmd -S <server> -E -d TalonDelivery -i sql/06_stored_procedures.sql
sqlcmd -S <server> -E -d TalonDelivery -i sql/07_uat_test_cases.sql     # expect 23/23

powershell erp_extracts/Export_Extracts.ps1
powershell excel/Build_Workbook.ps1
powershell excel/Validate_Workbook.ps1                                  # expect 16/16

# Power BI: open Desktop on a blank report first, then
powershell powerbi/Build_PowerBI_Model.ps1                              # click the credential prompt
powershell powerbi/Validate_PowerBI_Model.ps1                           # expect 28/28
```

**The gate is a separate step.** `04_data_quality_checks.sql` *creates* `usp_RunDataQualityChecks`; it does not run it. Executing the procedure is what applies the tolerance — it passes here at **1.779% against 2.000%**.

The QA gate raises rather than printing, so `sqlcmd -b` stops the sequence when it fails. It passes
here at 1.779% against a 2.000% tolerance; tighten `@MaxAffectedMustShipPct` to see it stop.

The generator is deterministic — hash-keyed rather than `RAND()` — so a rebuild reproduces the
dataset byte for byte, and UAT-22 asserts the fingerprints.

To browse the workbook without SQL Server, open `excel/Talon_Readiness_Control.xlsx` directly: it
ships with its data loaded.
