# Power BI build guide — Talon Robotics Payload Delivery Readiness

**Written for:** an analyst rebuilding this report from scratch against their own SQL Server.

> **Data disclosure.** Talon Robotics is a fictional mechatronics company. All data is synthetic and
> generated by the scripts in `sql/`. No confidential data is used and no claim is made about any
> production system.

---

## What is scripted and what is not

| Layer | How it is built | Why |
|---|---|---|
| Tables, columns, relationships, hierarchy | `Build_PowerBI_Model.ps1` | Reviewable, diffable, rebuildable |
| 53 DAX measures | `Build_PowerBI_Model.ps1` | So the readiness definition in DAX can be checked against the one in SQL |
| Report pages and visuals | **By hand, following §4** | There is no supported scripting path for the report layer |
| Verification | `Validate_PowerBI_Model.ps1` | Structural checks pass on an empty model; only querying it proves anything |

The scripts talk to the local Analysis Services engine Power BI Desktop exposes while a file is
open — the same mechanism Tabular Editor and DAX Studio use. There is no CLI for this.

---

## 1. Build the model

1. Run the SQL in order (`sql/01` … `sql/07`); expect **23/23** on the UAT suite.
2. Open **Power BI Desktop** on a blank report and leave it open.
3. `powershell powerbi/Build_PowerBI_Model.ps1`

On first run it downloads the official Microsoft AMO client package from nuget.org into
`.amo_libs/` (~6 MB, gitignored).

**The first refresh raises a credential prompt inside Desktop.** The script appears to hang until
you click through it — choose Windows / Integrated authentication and any privacy level. This
happens once per Desktop session, and again after the tables are dropped and recreated.

4. Save the file as `powerbi/Talon_Readiness_Model.pbix`.

## 2. Verify it before building anything on top of it

```
powershell powerbi/Validate_PowerBI_Model.ps1
```

Expect **28 of 28 checks reconcile**.

Do not skip this and do not substitute a glance at the field list. `Build_PowerBI_Model.ps1` reports
complete success against a model that loaded zero rows — creating tables and measures never touches
the data, and a Desktop refresh does not populate `EstimatedRowCount`.

Three of those checks go past the totals deliberately:

- the five verification states must **partition** the 519 requirements;
- `[Stale by Code] + [Stale by Requirement]` must equal `[Stale]`, so the buckets are exclusive;
- readiness is reconciled for **all eight subsystems individually**, not sampled.

A headline can agree while every cut beneath it is wrong, and the cuts are what the report pages
show. Project 3 in this portfolio shipped a measure that was correct for the one vendor anyone
checked and wrong for the other 35.

**One caveat, stated plainly:** this proves Power BI and SQL *agree*. It does not prove either is
right. Project 1 shipped an Excel workbook and a SQL view that agreed exactly and were both wrong,
because both came from the same flawed written definition.

## 3. The model

Twelve tables. Four dimensions (`Dim_Date`, `Dim_Subsystem`, `Dim_Person`, `Dim_Build`), five facts
loaded from SQL views (`Requirement`, `Queue`, `RAID`, `WorkItem`, `BuildChurn`), and two reference
tables plus `Ref_Reporting`.

Full measure-by-measure reasoning is in `DAX_Measures.md`. The three things to understand before
editing anything:

**Readiness is over must-ship only.** A percentage mixing must-ship and nice-to-have is arithmetic
with no decision attached.

**The stale buckets are mutually exclusive and ordered the same way as SQL.** A requirement stale on
both counts reports as "requirement changed", because that one needs a human before anyone re-runs
anything.

**`Ref_Reporting` pins the as-of.** Anchoring on the newest build would silently reassess against an
experimental build the moment one appeared after the release candidate.

### Measure folders

| Folder | Contains |
|---|---|
| `00 Reporting` | `As Of Build`, `As Of Date` |
| `01 Population` | Requirements, must-ship, should-ship |
| `02 The contrast` | Work-item completion, ship readiness, the gap |
| `03 Verification` | Coverage, policy compliance, the five states, staleness |
| `04 Queue` | Outstanding, rig hours, rig weeks, schedulable this week |
| `05 Churn` | Builds changed, lines changed, churn per readiness point |
| `06 RAID` | Open, overdue, critical, exposure |
| `07 Status` | RAG colour and status pairs |

## 4. Report pages (build these by hand)

### Page 1 — Can we ship?

The page exists to put two numbers beside each other. Resist adding anything that competes with
them.

Two large cards, side by side, same size:

| Card | Measure | Colour measure |
|---|---|---|
| Work items closed | `Work Item Completion %` | `Work Item Completion Colour` |
| **Ship readiness** | `Ship Readiness %` | `Ship Readiness Colour` |

Beneath them a single card for `Readiness Gap vs Reported`, and a text box carrying the sentence
the page is for:

> Both figures are true. Only one of them is about shipping. A verification is evidence about one
> build; if the subsystem has changed since, the green tick describes software that no longer exists.

Then a stacked bar of the five verification states — `Requirements` by
`Requirement[VerificationState]` — so the 41-point gap immediately decomposes into *why*.

Slicers: `Requirement[Priority]` (default **MustShip**) and `Dim_Subsystem[Criticality]`.

### Page 2 — Where the gap is

- Table: `Dim_Subsystem[SubsystemName]`, `Must Ship`, `Current Must Ship`, `Ship Readiness %`,
  `Builds Changed`, `Rig Hours Outstanding`, with `Ship Readiness Colour` on the readiness column.
- Scatter: `Builds Changed` (X) against `Ship Readiness %` (Y), one point per subsystem, sized by
  `Must Ship`. The two Safety subsystems sit bottom-right, and that shape *is* the finding — high
  churn, low readiness, most of the must-ship population.
- Card: `Churn per Readiness Point`.

Put the interpretation on the page: a subsystem that changed forty-five times and is 23% ready is
not behind on testing, it is still being designed.

### Page 3 — What to do next

- Table from `Queue` sorted by `PriorityRank`: rank, requirement, subsystem, type, owner,
  `ActionCode`, `RigHours`, `CumulativeRigHours`, `RecommendedAction`.
- Cards: `Outstanding`, `Schedulable This Week`, `Rig Weeks Outstanding`.
- Slicer on `Queue[IsThisWeek]` — **default it to True**, so the page opens on work that can
  actually be booked rather than on 226 rows nobody can action this month.
- Bar of `Outstanding` by `Queue[ActionCode]`, so the mix of *re-run* versus *raise the test level*
  versus *verify for the first time* is visible. Those need different people.

### Page 4 — Evidence quality

- Cards: `Under Levelled`, `Self Verified`, `Policy Compliance %`.
- Table: `Ref_VerificationPolicy` in full — `ReqType`, `MinTestLevel`,
  `RequiresIndependentTester`, `PolicyNote`. Showing the policy next to the breaches is what lets a
  reader disagree with the analysis on its own terms instead of dismissing it.
- Matrix: `Requirement[ReqType]` against `Requirement[VerificationState]`, values `Requirements`.
  Safety and Regulatory are the worst-covered types, and this is where that becomes visible.

### Page 5 — RAID

`RAID Open`, `Critical RAID Open`, `Overdue RAID %`, `Open RAID Exposure` as cards; a matrix of
`Probability` against `Impact` with `Open RAID Exposure` as values, which reproduces the risk matrix
in the shape a board already reads.

Note on the page that `IsOverdue` excludes items due before they were raised — seven of them exist,
they are a data defect, and counting them would blame the programme for a typing error.

## 5. Re-running

`Build_PowerBI_Model.ps1` is idempotent: it clears relationships first, then drops and recreates
every table and measure.

The order matters and is not obvious. **Removing a table does not cascade to the relationships that
reference it** — TOM leaves them dangling and then refuses the save with
`Relationship 'Relationship' points to deleted table 'Dim_Date'`. That error only ever appears on a
re-run, never on a first run, which is exactly the kind of thing a script gets shipped without.

Two smaller traps in the same area: `RelationshipCollection` exposes `Remove(object)` and not
`RemoveAt(index)`, and PowerShell's fallback for a missing method is to enumerate the collection and
try the method on each *member* — so `RemoveAt` fails with a message naming
`SingleColumnRelationship` rather than the collection. And the collection must be snapshotted with
`@()` before removing from it.
