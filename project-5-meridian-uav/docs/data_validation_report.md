# Data validation report — Meridian UAV Services

**Written for:** a reviewer assessing whether the figures in this project can be trusted, and an
analyst who might inherit it.

> **Data disclosure.** Meridian UAV Services is a fictional UAV operator. All data is synthetic and
> generated by the scripts in `sql/`. Degradation behaviour is modelled on publicly described
> characteristics of rotating machinery. No confidential data is used and no claim is made about any
> real aircraft, operator or manufacturer.

---

## 1. What "validated" means here

Four things, in order of how much they cost to do and how much they are worth:

| | What it proves |
|---|---|
| **The pipeline runs** | Nothing. Every script in this project ran clean while producing wrong numbers at some point. |
| **Planted defects are found** | The data-quality layer detects the specific problems the generator injected — by behaviour, never by a marker. |
| **Every figure is computed twice and reconciled** | The alert rule exists in T-SQL and in pandas; the compliance figures exist in SQL and in Excel formulas. They are required to agree exactly. |
| **The tests can fail** | Six cases deliberately break something and assert the detection fires. A suite that has only ever passed has not been shown to work. |

The fourth is the one this portfolio keeps learning. Every project in it has shipped at least one
defect past a green test run.

## 2. Planted defects, and whether they were found

The generator injects five defect classes by making the data **behave** wrongly. Nothing is tagged,
so a check that searched for a flag would find nothing in a real extract.

| Check | Class | Planted | Found |
|---|---|---:|---:|
| DQ-01 | Duplicate sortie records | 18 pairs | **36** ✓ |
| DQ-02 | Flight time with zero landings | 11 | **11** ✓ |
| DQ-03 | Sensor readings outside the fitted window | 13 | **13** ✓ |
| DQ-04 | Maintenance events before installation | 7 | **7** ✓ |
| DQ-05 | Components removed before installation | 6 | **6** ✓ |

DQ-01 reports 36 for 18 planted pairs, and that is correct: **both** copies are flagged, because
which one is genuine is unknowable. A check that guessed would be asserting something it cannot know.

Seven further checks (DQ-06 to DQ-12) found nothing and are reported anyway. A summary listing only
what it found cannot distinguish *we looked and it was clean* from *we never looked*. UAT-27 proves
DQ-06 can fire by creating an overlap and asserting the detection returns exactly 4 against a
baseline of 0.

### DQ-03 nearly reported one root cause 358 times

The first run of DQ-03 returned **370** findings against 13 planted. Every one was individually
correct. Six installs have dates that run backwards (DQ-05), so their "fitted window" is not a
window, so *every* reading on them falls outside it — 349 collateral findings from six malformed date
fields.

DQ-03 now suppresses the cascade and reports 13. The six root causes are reported once each by
DQ-05. Reporting a consequence as an independent finding is how a data-quality summary loses its
reader: the list looks catastrophic, the fix list has six items on it, and nothing in the report says
which.

## 3. The QA gate, and the two definitions it had

The gate does not count defective rows. A defect count answers *how messy is this data*, and nobody
makes a decision with that.

**First definition — rejected.** A flight-critical component was "affected" if any flagged sortie was
counted into its hours. It failed at **22.50%** against a 3% tolerance and the number was
meaningless: a duplicated sortie adds about 2.5 stress hours to a 150-hour interval — a 1.7% error
that only changes an answer if the component is within 2.5 hours of its threshold.

**Second definition — shipped.** A component's verdict is unsafe when the **uncertainty band** is
wider than its **margin** to the threshold:

- duplicate sorties contribute the excess copies (which copy is genuine is unknowable, so all but one
  are treated as possibly not having happened);
- zero-landing sorties contribute the *missing* cycle stress, estimated from the landings its profile
  actually records — this one points the other way, the recorded figure is too **low**;
- post-retirement sorties contribute the whole sortie.

It is a two-sided test: it does not matter whether the error flatters or maligns the component, only
whether the conclusion depends on it.

**It passes at 0.000% against a 3.000% tolerance.** That is a clean result rather than a narrow one,
and it is worth saying plainly: on this dataset, no flight-critical component sits close enough to
its threshold for the known-bad data to move it across.

## 4. Defects found in this project's own code

This is the section worth reading. Everything below was found **after** the code was written, ran
clean, and produced plausible numbers.

### 4.1 Found while building

**A hard-coded loop bound that suppressed the finding it was built to demonstrate.**
The wear simulation advanced every component position by one generation per pass, capped at six —
which looked generous against a 150-hour interval and roughly 560 flight hours per airframe. It is
wrong for exactly the aircraft this project is about: a Highland airframe burns a rotor set every
~69 flight hours and needs seven generations — one more than the cap allowed. Generation seven was
created and never closed, so those parts sat permanently fitted with their life exhausted and
**never failed**. The bug quietly
argued against the finding. The loop now runs until a pass closes nothing, and a gate asserts no
fitted component has exhausted stress life — on *both* clocks, because a version checking only the
physics clock would let stranded scheduled removals through, and that is the direction that flatters
the fleet.

**A Weibull scale set at the mean rather than at B10.**
Component lives were drawn around the published interval, so roughly half of every population failed
before its scheduled replacement and the fleet ran at **80% unscheduled removals**. A fleet like that
would be grounded. Real intervals are set at the **B10 life** — the point by which 10% of the
population has failed — so the scale is now derived: `scale = interval / (−ln 0.9)^(1/shape)`. The
contrast between bases survived the correction and sharpened.

**Determinism that was claimed and did not exist.**
Every pseudo-random draw was keyed on a surrogate `IDENTITY` value. `INSERT … SELECT` assigns those
in **unspecified** order, and the airframe rows are generated from `sys.all_objects`, whose row order
changes when the database's object list changes. Adding one reference table was enough to hand
`MU-017` a different key, which permuted which airframe flew on which day: the sortie count moved
from 10,346 to 10,288 and every fingerprint changed, **with no edit to any generation logic**. Every
draw is now keyed on a business key — `TailNumber`, `SortieID`, `ComponentSerial` — and the fix is
verified by regenerating under a deliberately changed object catalog.

**`TOP (n)` presented as a sample.** The defect injection read
`UPDATE TOP (11) … WHERE fn_Rand(...) < 0.004`. About forty rows satisfy that predicate and `TOP`
takes eleven of them, with no `ORDER BY` and no guarantee which. Every block now orders the whole
candidate set by a hash of its business key and takes the first *n*.

**An arithmetic overflow caused by evaluation order.** `TempRiseC` is `DECIMAL(5,2)` and is computed
as `14 + 17 × f²`. Inside the fitted window `f ≤ 1`; the join matched on airframe alone and relied on
the `WHERE` clause to drop sorties outside it. SQL Server does not promise to filter before
evaluating the `SELECT` list, and did not. **The fix was not to clamp `f`** — a clamp would make the
expression incapable of overflowing and therefore incapable of reporting that the join was wrong.
The filtered rows are materialised first.

**A window function dragged into a `GROUP BY`.** `PERCENTILE_CONT` has no aggregate form, so putting
it in a grouped query forces its arguments into the grouping key. `fn_AlertSummary` returned dozens
of rows per component instead of one — `Population 1`, `Precision 0.00` — every row individually
well-formed, nothing NULL, nothing raised. **The creation gate tested four of the five functions in
the file.** Gates now assert the *grain* each function promises, not merely that it returns rows.

**Three `VARCHAR` truncations**, all in reference-table note columns. The pattern is identical every
time: the reasoning outgrows a width chosen before the reasoning existed. The columns are now 400.

### 4.2 Found by adversarial review

A multi-agent review of the SQL raised 51 findings. **49 of its 55 verification agents died on a
session quota**, so the run reported 50 as "refuted" when they had simply never been checked.
*Unverified is not refuted* — the findings were re-verified by hand against the live database. Ten
were confirmed as real defects.

| | Defect | What it did |
|---|---|---|
| **A** | `AirframeStatus = 'Active'` used as the *as-of* population filter | Every historical figure computed over **today's** fleet |
| **B** | Component windows inclusive at both ends | **1,144 sorties** charged to two components at once |
| **C** | `vw_SensorFeatures` had no install-window predicate | **362 orphan readings** trained the model and raised alerts |
| **D** | Date-inverted installs scored as real lives | **5 of 288** published true positives had no measurable life |
| **E** | `AffectsCurrentWear` could never be set | **0 of 73** findings flagged; the column was dead |
| **F** | UAT-09's zero-row guard used `OR` where `AND` was meant | Passed when the function returned nothing |
| **G** | DQ gate: `NULL > 3.000` is false | Printed "Gate PASSED" on an empty population |
| **H** | TRAINING payload coefficient sign inverted | Light payload *added* stress; the code contradicted its own comment |
| **I** | `Ref_StressModel` has no component dimension | A documented planted pattern was not implemented as described |
| **J** | `ComponentHoursAtEvent = 0` on all 39 retirement events | `ISNULL` hiding an unpopulated code path |
| **K** | UAT-27 tested a **copy** of DQ-06 pasted into the test | Breaking the shipped check left the test green |
| **L** | Fingerprint blind to airframe, profile and date | A rebuild could reassign the whole fleet's workload and match |

**A is the one that stings.** `03_core_views.sql` carries a long header about Project 4's defect — a
function that took `@AsOfDate` and answered about "now" for one metric — and then filtered the
population on a current-state attribute. MU-003 retired in September 2025; at an as-of date of June
2025 it was flying, and the code excluded it. The availability denominator read **28.00 at every date
across an eighteen-month trend** while the numerator moved.

UAT-10 passed over it, because UAT-10 asserted that each metric *changes* between dates. It does
change — the numerator moves. **Asserting that a number moves does not prove it moves correctly.**
UAT-30 now asserts the denominator.

**L is the quietest.** `CHECKSUM_AGG` aggregates by XOR, so any two rows with an equal checksum
cancel and become invisible; 142 sensor readings were in exactly that position. And the fingerprint
omitted `AirframeKey`, `MissionProfileKey` and `SortieDateKey` — the three columns that decide which
stress multiplier applies, which base it lands on, and which component accrues it. A rebuild could
have reassigned every sortie to a different aircraft flying a different profile on a different day
and reproduced the fingerprint exactly. It is now `SUM` over `BIGINT` and covers all three.

### 4.3 Found by the tests themselves

**UAT-27 and UAT-28 vanished without failing.** The suite reported "26 of 28 expected" and raised.
Project 4 taught this portfolio to create `#UATResults` *outside* the fixture transaction so
`ROLLBACK` could not drop it — and the `INSERT`s were written *inside* it. Temp-table writes are
transactional, so the rollback discarded the two result rows along with the fixture. Both cases had
executed and both had passed. Without the expected-case guard the run would have printed "24 passed,
2 failed" with nothing indicating that two cases had disappeared. The verdicts are now captured in
variables that survive the rollback.

**UAT-08 caught a specification split.** After the handover rule was corrected, the "independent"
reconciliation failed by 0.65 flight hours — because it was still summing from the install date, the
old inclusive-at-both-ends window. The failure was correct: the two sides were implementing different
specifications, so agreement would have meant nothing. A reconciliation test must restate the **same
rule** a different way, not a different rule.

**UAT-10 failed on a coincidence.** Comparing two dates, `AirframeAvailabilityPct` and
`OverdueFlightCritical` were identical fifteen months apart — 26 of 28 airframes available on both
dates, 91 overdue on both. Neither was ignoring the parameter. Two-point equality cannot distinguish
*did not move* from *came back to the same place*; the case now requires more than one distinct value
across six dates.

### 4.4 An error in the review itself

While verifying a finding about index design, this analysis queried `sys.index_columns` ordered by
`key_ordinal` and concluded that `IX_Sortie_Airframe_Date` was keyed on measures rather than on
airframe and date. **That was wrong.** Included columns carry `key_ordinal = 0` and therefore sort
first; the DDL is correct. Recorded here because a validation report that lists only the errors it
found in other people's work is not a validation report.

## 5. Reconciliation

Every headline figure is computed at least twice, in different tools, and required to agree.

| Figure | Implementation A | Implementation B | Result |
|---|---|---|---|
| Alert confusion matrix | `fn_AlertEvaluation` (T-SQL) | `evaluate_alerts` (pandas) | **population, TP, FP, FN, actionable — all exact** |
| Hour / stress compliance | `fn_FleetKPI` (T-SQL) | `COUNTIFS` on the Dashboard (Excel) | 16 of 16 workbook checks |
| Accrued component hours | `fn_ComponentWear` | direct sum over `Fact_Sortie` | UAT-08, within per-sortie rounding |
| Queue capacity cut | `fn_ActionQueue` | Excel `SUMIFS` running total | validated by re-opening the workbook |

The pandas/T-SQL reconciliation is the one that earned its keep: it reported 2 false negatives where
T-SQL reported 3. T-SQL was right. pandas built its population from the *readings*, so a monitored
component that produced **no telemetry at all** did not exist in its evaluation — and a component the
monitoring system never saw cannot be alerted on, so it is a guaranteed miss. Excluding it flatters
recall. **A component with no condition monitoring is not "not at risk". It is invisible, and
invisibility is a miss.**

**One caveat, stated plainly:** this proves the implementations *agree*. It does not prove either is
right. Project 1 shipped an Excel workbook and a SQL view that agreed exactly and were both wrong,
because both came from the same flawed written definition.

## 6. Known limitations

**The stress model has no component dimension.** A landing costs a rotor assembly exactly what it
costs the landing gear. Physically that is wrong. Modelling per-component damage coefficients needs
six times the reference data and a source for each cell, and this project has none. The comparison it
was built for — two airframes flying different work accrue different damage per logged hour — does
not depend on the missing dimension, but differences *between component types* come from their
Weibull shapes and intervals, not from any component-specific response to landings.

**The stress multipliers are the most contestable input in the project.** Whether mountain work
really costs 2.4× coastal is exactly the argument a maintenance engineer should be having. The
numbers live in `Ref_StressModel` with their reasoning attached, so that argument can be had against
the table rather than against a `CASE` expression nobody can see.

**The alert threshold and the precision floor are policy, not findings.** Both are parameters. The
recommendation changes if the floor changes, and `usp_RecommendedThresholds` takes it as an argument
for that reason.

**A model trained on synthetic degradation learns the generator.** The AUC figures in `python/` are
not a claim about real rotor bearings. What transfers is the *method*: evaluate on actionable lead
time, split by component and by time, and check whether the signal is in the telemetry or in the
exposure. The specific numbers describe this dataset.

**Seven of the twelve data-quality checks have never fired on real data.** DQ-06 is exercised by a
negative fixture. The other six are not, and a check that has never fired is a check nobody has
tested — that is a known gap, not a claim of completeness.
