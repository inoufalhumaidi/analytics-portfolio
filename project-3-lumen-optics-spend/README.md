# Project 3 — Lumen Optics Manufacturing: Photonics Spend Scorecard

**Our purchase prices are flat or falling and every variance report is green — so why is material
cost per accepted unit rising, and which supplier–part combinations should sourcing renegotiate
first?**

*Stack: T-SQL (SQL Server) · Power BI (DAX) · Excel*

> **Data disclosure.** Lumen Optics Manufacturing is a fictional photonics manufacturer. All data
> is synthetic and generated by the scripts in `sql/`. No confidential data is used and no claim
> is made about any production system.

---

## The answer

| | |
|---|---:|
| Purchase price variance | **−0.19%** · Green |
| **Erosion capture** | **29.50%** · Red (target 80%) |
| **Annual value of the gap** | **$4,047,609** |

Every variance report is green while **8.3% of annual direct-materials spend** walks out the door.

`✦` **Why PPV cannot see it.** Optical components follow learning curves — laser diodes decline
about 8% a year, connectors 7%, coatings 5%. A supplier who renews a contract **flat** keeps
everything the curve was supposed to hand back, and because the price never *rose*, purchase price
variance records zero. Forever.

**And the gap is worst exactly where leverage is weakest:**

| | Pairs | Opportunity | Avg leverage | **Erosion captured** (spend-weighted) |
|---|---:|---:|---:|---:|
| Parts with 2+ qualified suppliers | 152 | $2,576,657 | 72.8 | **38.26%** |
| **Parts with one qualified supplier** | **33** | **$1,470,952** | **38.1** | **8.91%** |

Suppliers hold price precisely where Lumen cannot leave — **4.3× less of the curve captured**
where there is no credible alternative.

`✦` Both figures are **spend-weighted**, on the same basis as the 29.50% headline. An earlier
version of this table quoted the simple averages (37.77% and 10.88%), which are not comparable to
the headline and understated the gap: weighting by money widens it from 3.5× to 4.3×. The method
matters here precisely because the pairs are so unequal in size.

## Three modelling decisions worth reading

**A price agreement is a dated fact, not an attribute.** A contracted price is true between two
dates and false outside them. Storing it on the part or the vendor would let today's contract
retroactively govern a purchase made two years ago. Two consequences the code handles explicitly:
an **open-ended** agreement is still in force (excluding `NULL` end dates is how contract coverage
is made to look far worse than it is), and **overlapping** agreements make the contracted price
ambiguous — so resolution is deterministic by construction and the ambiguity is *reported* rather
than silently resolved.

**Receipts carry acceptance, not just quantity.** In optics a component can arrive, be counted,
and still be unusable. If a receipt records only quantity, the cheapest supplier by unit price
always wins because the cost of what they shipped that could not be used is invisible.

**The erosion benchmark is a reference table, not a constant in a query.** It is the single most
contestable input in the analysis, so it lives in `Ref_PriceErosionBenchmark` with a `SourceNote`
on every row — where a category manager can see it, challenge it and change it.

## The cheapest supplier is the most expensive one

Part LOM-0072, three qualified suppliers:

| Vendor | Avg unit price | Acceptance | **Cost per accepted unit** |
|---|---:|---:|---:|
| **VEN-004** | **$184.14** (cheapest) | 91.61% | **$204.71** |
| VEN-012 | $197.43 | 98.99% | **$204.44** ← cheaper |
| VEN-009 | $211.49 | 99.09% | $213.94 |

A 6.7% price advantage entirely erased by rejections. Across the book, **$1,571,168** of material
was paid for and cannot be used.

`✦` "Avg unit price" is the simple average across that vendor's lines — the number a category
manager reads off a price list. Cost per accepted unit is necessarily quantity-weighted, because it
is a total divided by a total. Weighting the price column the same way would only sharpen the
point: VEN-004 comes out at $183.81 against VEN-012's $198.72, a 7.5% advantage rather than 6.7%,
and still loses on cost per accepted unit.

## The renegotiation queue

185 vendor–part pairs is not a plan. A category manager can run perhaps eight serious negotiations
a quarter, so the queue stays complete for audit and marks what is workable.

**43 pairs this quarter, carrying 65.6% of the $4.05M opportunity.**

| Action | Pairs | Opportunity | This quarter |
|---|---:|---:|---:|
| `RENEGOTIATE` | 54 | $1,631,840 | 16 |
| `PUT_ON_CONTRACT` | 48 | $1,623,978 | 19 |
| `DUAL_SOURCE` | 8 | $515,330 | 8 |
| `ACCEPT` | 73 | $276,461 | 0 |
| `FIX_QUALITY` | 2 | — | 0 |

**Ranking is by money; the ACTION is by leverage.** The largest gaps sit on sole-source parts where
there is no credible threat to make — ranking on value alone sends a category manager into
meetings they cannot win. Quality outranks price: if the loss is rejected material, a price
conversation is the wrong conversation. And above $100,000 a year you ask anyway, because weak
leverage is a reason to expect a hard conversation, not a reason to skip one.

## The Excel workbook

`excel/Lumen_Spend_Scorecard.xlsx` — **a control, not a report.**

Nothing on the Dashboard is a pasted number. Balances come from `SUMIFS` over the purchase-order
extract, the red/amber/green status from `INDEX`/`MATCH` against the target table, and the
Validation sheet holds each Excel figure against the one SQL produced independently. All **14**
checks reconcile.

**No dynamic-array formulas** — `FILTER`, `SORT` and `UNIQUE` would break the file on Excel 2019
and LibreOffice.

## Data quality

The gate **passes at 0.497% against a 0.500% tolerance** — by three thousandths of a percentage
point. That is luck, not comfort, and the report says so.

More usefully: the **largest defect by value is deliberately outside the calculation**.
`AMBIGUOUS_CONTRACT` at $1,495,917 does not mis-state how much was spent — it mis-states whether
the purchase price variance computed on that spend means anything. A ratio problem, not a total
problem.

## The Power BI model

`powerbi/Build_PowerBI_Model.ps1` scripts the whole semantic model — 10 tables, 10 relationships and
**69 DAX measures** — into a running Power BI Desktop session through the local Analysis Services
engine it exposes. Sixty-nine measures clicked into a UI cannot be reviewed, diffed or rebuilt;
scripted, they sit in source control beside the SQL that feeds them, and a reviewer can check that
the leverage weights in DAX are the same weights the SQL uses.

`powerbi/Validate_PowerBI_Model.ps1` then queries the model **in DAX** and reconciles 31 figures
against the SQL that produces them — including the cost index for all 36 vendors individually.
**31 of 31 reconcile.**

That validator is not optional decoration. The build script reports complete success against a
model that loaded zero rows, because creating tables and measures never touches data. And the first
version of `Cost Index vs Best` returned exactly **100.00** for every filtered vendor — the inner
`MINX` intersected with the outer vendor filter, so each vendor was compared against itself. A
number that is exactly 100 on a "100 = best available" index looks like a correct answer.

## Defects worth reading about

**A planted pattern that silently did not exist.** The generator was told to make one named vendor
the cheap-but-rejected laser diode supplier, but vendor–part assignment is random and that vendor
was never assigned a laser diode. The `UPDATE` matched zero rows — which is not an error in SQL.

**A lapse that produced an eternal contract.** Non-renewal deletes the later contract terms, then
the surviving final term was marked open-ended — so a contract that lapsed became one that never
expires. Caught because off-contract spend stayed at *exactly* 222 lines across two runs while the
lapse rate was doubled. A number that refuses to move when its driver changes is evidence.

**A window function that saw one row.** `ROW_NUMBER() OVER (PARTITION BY …)` inside a `CROSS APPLY`
evaluates over the single applied row, so first price and last price became the same number and
the analysis reported *"100% of vendor–part pairs holding price flat"* — contradicting the table
directly above it.

Full write-ups in [docs/data_validation_report.md](docs/data_validation_report.md).

## Running it

```bash
sqlcmd -S <server> -E -d master     -i sql/01_create_schema.sql
sqlcmd -S <server> -E -d master     -i sql/02_generate_synthetic_data.sql
sqlcmd -S <server> -E -d LumenSpend -i sql/03_core_views.sql
sqlcmd -S <server> -E -d LumenSpend -i sql/04_data_quality_checks.sql
sqlcmd -S <server> -E -d LumenSpend -Q "EXEC dbo.usp_RunDataQualityChecks"   # the gate
sqlcmd -S <server> -E -d LumenSpend -i sql/05_kpi_views.sql
sqlcmd -S <server> -E -d LumenSpend -i sql/06_stored_procedures.sql
sqlcmd -S <server> -E -d LumenSpend -i sql/07_uat_test_cases.sql     # expect 21/21

powershell erp_extracts/Export_Extracts.ps1
powershell excel/Build_Workbook.ps1
powershell excel/Validate_Workbook.ps1                               # expect 14/14

# Power BI: open Desktop on a blank report first, then
powershell powerbi/Build_PowerBI_Model.ps1                           # click the credential prompt
powershell powerbi/Validate_PowerBI_Model.ps1                        # expect 31/31
```

**The gate is a separate step.** `04_data_quality_checks.sql` *creates* `usp_RunDataQualityChecks`; it does not run it. Executing the procedure is what applies the tolerance — it passes here at **0.497% against 0.500%**, which is a margin of three thousandths and is reported as a margin rather than as a green light.

`dbo.usp_RunDataQualityChecks` is the QA gate, and it **raises** when the mis-statement exceeds
tolerance rather than printing and returning zero — so `sqlcmd -b` stops the sequence. It passes
here at 0.497% against a 0.500% tolerance, so the build completes; tighten
`@MaxMisstatementPctOfSpend` to see it stop.

The generator is deterministic — hash-keyed rather than `RAND()` — so a rebuild reproduces the
dataset byte for byte, and UAT-20 asserts the fingerprints.

To browse the workbook without SQL Server, open `excel/Lumen_Spend_Scorecard.xlsx` directly: it
ships with its data loaded.
