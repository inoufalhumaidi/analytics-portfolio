# Data Validation Report
## Lumen Optics Manufacturing — Photonics Spend Scorecard

**Reporting date:** 2025-12-31  
**Dataset:** 6,327 purchase-order lines · 6,127 goods receipts · 660 price agreements · 140 parts · 36 vendors  
**Status:** validated — 21/21 acceptance tests pass, 14/14 SQL-versus-Excel checks reconcile

> **Data disclosure.** Lumen Optics Manufacturing is a fictional company. Every figure is
> synthetic and generated by the scripts in `sql/`. No confidential data is used and no claim is
> made about any production system.

---

## 1. What "validated" means here

A dataset is not validated because a query returned rows. It is validated when the things that
would let it produce confident, plausible, wrong answers have each been tested and found not to be
happening.

| Mechanism | Catches | Blind to |
|---|---|---|
| **Constraints and creation gates** | Structurally impossible rows | Anything internally consistent but wrong |
| **Behavioural data-quality checks** (`sql/04`) | Records individually valid but collectively impossible | Defects that look like normal business behaviour |
| **Cross-implementation reconciliation** | A metric implemented twice that disagrees | A definition wrong in the same way twice |
| **Cross-dimensional profiling** | Patterns visible only when two cuts are combined | Whatever nobody thought to cross |

The fourth row earned its place three times on this build (§3.1, §3.2, §3.3).

## 3. Defects found during the build

### 3.1 A planted pattern that silently did not exist — fixed

The generator was instructed to make one named vendor the cheap-but-rejected laser diode supplier.
Vendor–part assignment is random, and that vendor was never assigned a laser diode part. The
`UPDATE` matched **zero rows**, which in SQL is not an error. It did nothing, reported nothing, and
the pattern was simply absent.

It surfaced only because the profiling query listed acceptance rates by vendor for the category
and the named vendor was not in the output at all.

**Fix:** derive the target from the data rather than asserting it —

```sql
SELECT TOP 1 CheapVendorKey = pv.VendorKey, CheapVendorID = v.VendorID
INTO #Flags
FROM #PartVendor pv ... WHERE pv.Category = 'Laser Diode' AND pv.SupplierRank = 1
GROUP BY pv.VendorKey, v.VendorID ORDER BY COUNT(*) DESC, pv.VendorKey;
```

— and have both the price logic and the rejection logic read the same `#Flags` row, so they cannot
disagree about which vendor the pattern belongs to.

### 3.2 A lapse that produced an eternal contract — fixed

Non-renewal is simulated by deleting later contract terms. The surviving final term was then
marked open-ended, so a contract that **lapsed** became one that **never expires** — the exact
inverse of the intended behaviour, and it left contract coverage looking perfect.

**How it was caught:** not by an error. Off-contract spend stayed at **exactly 222 lines** across
two runs while the lapse probability was more than doubled. A figure that refuses to move when its
driver changes is either a no-op or a broken dependency.

**Fix:** record how many terms were planned before deleting, and give a truncated chain a real
expiry date instead of an open one. Off-contract spend then responded to the parameter as
expected, and was tuned to 27.09%.

### 3.3 A window function that saw a single row — fixed

A pair-level erosion query reported *"185 of 185 vendor–part pairs flat or rising — 100%"*, which
directly contradicted the category table printed above it showing prices falling.

The cause was `ROW_NUMBER() OVER (PARTITION BY …)` inside a `CROSS APPLY`. The window function
evaluates over the single row it was applied to, so every row received rank 1 both ascending and
descending — making first price and last price the same number, and the comparison trivially true.

Rewritten as a windowed CTE over the whole set, the same analysis returned a genuine distribution
(33.5% of pairs flat or rising). **The defect was in the analysis query, not the data**, which is
the more dangerous case: nothing downstream would ever have flagged it.

### 3.4 Published figures that disagreed with their own components — fixed

`ExpectedPrice` was computed from an unrounded exponent while `YearsElapsed` was published rounded
to three decimals, so a reader redoing the arithmetic from the printed numbers got a different
answer. The same applied to `ErosionCapturePct` against `ActualErosionPct`.

Caught by **UAT-05** and **UAT-07**. The rule now applied in SQL, DAX and Excel alike: **a derived
figure is computed from its components as published, not from their unrounded intermediates.**

This also moved the headline opportunity from $4,047,570.34 to **$4,047,608.72** — a $38.38 shift
that then caused a workbook validation failure, because the validator still held the old constant.
A stale expectation is a failure worth having: it proves the check is actually comparing.

### 3.5 One defect reported twice — fixed

Duplicated PO lines are inserted after receipts are generated, so they can never have a receipt.
Every one was therefore also being reported as `NEVER_RECEIVED`, padding the defect count with a
direct consequence of a defect already on the report.

Excluding already-flagged duplicates dropped the count from 114 to **94** and took
`NEVER_RECEIVED` to zero. **UAT-16** is the regression guard.

### 3.6 Ownership assigned by key order — fixed

The renegotiation queue assigned each pair to a category manager using `MIN(BuyerKey)`. A review
query showed **140 of 185 pairs are bought by more than one person**, so for three quarters of the
queue the assignment was an accident of key ordering rather than who actually buys the part.

Now assigned to the buyer who placed the most spend on that pair in the trailing twelve months.
**UAT-11** asserts it.

## 3d. A join fan-out in the vendor scorecard, and a test that could not fail

**Symptom:** none. `CostIndexVsBest` sat between 100 and 110 for every vendor, exactly where a
like-for-like cost index should sit. `UAT-12` passed. The Excel workbook agreed. The figure had
been exported, loaded into the workbook's Vendor Scorecard sheet, and fed into a published ranking.

**The defect.** `fn_VendorScorecard` computed the index as

```sql
CostIndexVsBest = 100.0 * SUM(pv.Landed) / NULLIF(SUM(pb.BestCPA * pv.Accepted), 0)
...
FROM C c
JOIN PartVendor pv ON pv.PartKey = c.PartKey AND pv.VendorKey = c.VendorKey
JOIN PartBest   pb ON pb.PartKey = c.PartKey
GROUP BY c.VendorKey
```

`C` is at **PO-line** grain. `pv` is a **pair-level aggregate**. So `SUM(pv.Landed)` added each
pair's total landed cost once for every PO line in that pair — a join fan-out.

What makes it survive review is that both sides inflate. The numerator and the denominator are each
multiplied by the pair's line count, so the ratio stays finite, stays above 100, and stays entirely
plausible. But the line counts differ *per pair*, so they are not a common factor: the result is a
line-count-weighted average of the index rather than the index.

| | Value |
|---|---:|
| Vendors with a wrong index | **36 of 36** |
| Largest error | **3.07 index points** (VEN-018: 101.38 published vs 104.45 actual) |
| Vendors whose **rank position** moved | **33** |

And the index is not decorative: it carries **40% of the weight** in `usp_VendorRanking`'s
`CompositeScore`, the single figure the procedure is designed to be sorted on.

**Why `UAT-12` did not catch it.** The test asserted:

> `CostIndexVsBest` is at least 100 for every vendor (100 = best available)

That is true under *any* positive weighting of the pairs, including the wrong one. The assertion
could not fail for the reason the test existed. It is a specific instance of a general trap: a test
that checks a *property* of the answer (non-negative, bounded, monotonic) rather than the *value*
will pass through any transformation that preserves that property — and a fan-out preserves all
three.

**The fix.** The index is a pair-grain quantity, so it is now aggregated at pair grain in a separate
`VendorIndex` CTE and read back with `MAX()` — which, over a value constant within the group, means
"read the pre-aggregated figure" rather than recomputing it across lines.

`UAT-12` now recomputes the index independently at pair grain and asserts equality to 0.01, in
addition to the `>= 100` property check. Against the old implementation it fails on all 36 vendors.

**A second issue found in the same function.** Duplicated requisitions were excluded with
`PONumber NOT LIKE 'PO-D%'` — reading the generator's planted prefix. That is precisely what
`UAT-15` exists to prove the data-quality layer does *not* do, and the file containing that check
says so in a comment two hundred lines above. On this dataset the prefix test and the behavioural
test return the identical 26 lines, which is why it survived; on real data there is no `PO-D`
prefix and the exclusion would have matched nothing at all. Duplicate detection is now a single
shared definition, `fn_DuplicatePOLines`, used by the data-quality layer, the vendor scorecard and
the Power BI model alike.

**Restated figures.** Vendor cost indices changed for all 36 vendors (max 3.07 points) and
`usp_VendorRanking`'s composite score changed accordingly. No headline KPI moved: the index feeds
the vendor ranking, not the spend scorecard, and `fn_SpendKPI` never referenced it. Committed spend
is unchanged at $142,314,429.11 — `UAT-13` asserts it, and it holds under both the old prefix test
and the new behavioural one.

## 3e. The cohort table used a different average from the headline

**Symptom:** none. Two plausible percentages in a two-row table, both in the right range, both
telling the intended story.

`fn_SpendKPI` computes erosion capture **spend-weighted**, and says why in a comment: *"a pair with
$4m of spend and one with $40k should not count equally"*. The 29.50% headline is that figure. But
the cohort breakdown published in the README and the case study — the sole-source versus
multi-source split that is the project's second-biggest finding — was computed as a **simple
average** across pairs.

| | Simple average (published) | Spend-weighted (correct) |
|---|---:|---:|
| Parts with 2+ qualified suppliers | 37.77% | **38.26%** |
| Parts with one qualified supplier | 10.88% | **8.91%** |
| Gap | 3.5× | **4.3×** |

Two things are wrong with the published version, and only one of them is the number:

1. **It is not comparable to the headline it sits beneath.** A reader is invited to see 29.50%
   overall decomposing into 37.77% and 10.88%; those are three figures on two different bases.
2. **It contradicts the project's own stated method** — the same method is asserted in
   `fn_SpendKPI`, restated in `powerbi/DAX_Measures.md`, and given as a reason in
   `powerbi/POWER_BI_BUILD_GUIDE.md`. Writing the principle down three times did not make the
   table follow it.

The error happened to run *against* the argument: the correct weighting widens the sole-source gap
from 3.5× to 4.3×. That is worth noting, because it is the direction that makes a mistake hardest
to catch by reading — nothing looks overstated, so nothing prompts a check. Had it inflated the
finding it would likely have been questioned sooner.

**Why no test caught it.** There is no test. `UAT-07` asserts that `ErosionCapturePct` equals actual
erosion over benchmark *per pair*, and the workbook reconciles the 29.50% portfolio figure — but the
cohort split exists only in prose, computed once by hand and pasted into two documents. Every
number that appears in a document and nowhere in the codebase is in this category, and this is the
argument for keeping published figures in a view or an extract even when they are only ever read by
a human.

**The fix.** Both figures restated spend-weighted, both table headers now say *(spend-weighted)*
explicitly, and both documents state the basis alongside the number rather than leaving it implied.

## 3f. The QA gate printed FAIL and returned success

`usp_RunDataQualityChecks` ended its failure branch with a `PRINT`:

```
QA GATE: FAIL -- spend mis-stated by 0.497%, above the 0.100% tolerance.
```

and then returned **exit code 0**. `sqlcmd -b` reported success, so no build step, scheduler or
pipeline could act on it. The README described this as *"10 behavioural checks + a gate that can
fail the build"*; it could not fail anything.

The word FAIL appearing in the output is what hid it. Reading the console, the gate looks like it
works — the failure is only visible to something that checks the exit code, and nothing did until
one was checked explicitly.

Now `THROW`s. Verified both directions: at the default 0.500% tolerance the gate passes and sqlcmd
exits 0; at 0.100% it prints the same message and exits 1.

Worth recording that Project 1's data-quality gate had the identical defect, found the same day.
Both were written the same way, and in both the printed word "FAIL" stood in for a mechanism.

1. **It passes by three thousandths of a percentage point.** That is luck, not comfort. A

   it and this report would be wrong not to mention it.

`CountsTowardExposure` exists to stop double counting: a duplicated PO line is the cause, and the
overstated committed spend it produces is the effect, and they are the same dollars.

## 7. Structural assertions

Verified by `sql/07_uat_test_cases.sql`, **21 of 21 passing**.

| Property | Test | Why it would matter if it broke |
|---|---|---|
| Landed cost identity holds on every line | UAT-01 | One definition underpins every downstream figure |
| As-of snapshot counts only orders and receipts by then | UAT-02 | Otherwise historical spend improves whenever a later receipt lands |
| Open-ended agreements are still in force | UAT-03 | Excluding NULL end dates reports governed spend as maverick |
| Off-contract lines carry NULL variance, not zero | UAT-04 | Scoring zero reports perfect compliance for unnegotiated spend |
| Expected price matches the benchmark curve exactly | UAT-05 | The entire opportunity is the distance from this curve |
| Erosion windows cannot overlap | UAT-06 | Overlap averages the same orders into baseline and current |

| Every queued pair has one known action and an instruction | UAT-08 | A row with no instruction is not a control |
| Nothing material is parked as `ACCEPT` | UAT-09 | Parking six figures because a supplier is large gives money away |
| Category-manager capacity is respected | UAT-10 | A 185-row list is a ledger, not a plan |
| The assigned buyer is the one who places the spend | UAT-11 | Regression guard on §3.6 |
| Cost index is never below 100 | UAT-12 | Below 100 would mean the comparison is not like-for-like |
| Vendor scorecard ties to line level | UAT-13 | A fan-out join invents or loses money |
| Procedures reject invalid arguments | UAT-14 | A silent fallback answers a question nobody asked |
| The duplicate detector fires on the planted defects | UAT-15 | An untested detector is an assertion |
| No defect is reported twice | UAT-16 | Regression guard on §3.5 |
| Overlapping agreements are detected | UAT-17 | A variance without its ambiguity has no error bar |
| Contract resolution is deterministic | UAT-18 | Otherwise the same report gives different variances per run |
| Accepted + rejected = received on every receipt | UAT-19 | A receipt that does not add up breaks every yield figure |
| The generator is deterministic | UAT-20 | Quoted figures must be re-checkable |
| Opportunity is never negative, and the offset is disclosed | UAT-21 | Netting implies an offset nobody can realise |

### Three tests that failed on their own premises

Worth recording, because the instinct on a red test is to suspect the code:

1. **UAT-05/07** compared a published rounded figure against an unrounded recomputation. The
   *code* was then changed — correctly — to match the principle the test was asserting.
2. **UAT-13** compared vendor-level committed spend against received-only line spend. The
   **test** was wrong; the scorecard reports committed spend on purpose, with acceptance and the
   cost index computed only over what has arrived.
3. The workbook validator held a stale constant from before the §3.4 rounding fix. **The
   expectation** was wrong, not the workbook.

A failing test means the code and the assertion disagree. Which of the two is wrong is a separate
question, and answering it the wrong way breaks a correct implementation to satisfy a bad
assertion.

## 8. Known limitations

1. **Erosion is measured from the first observed price.** The model detects a failure to decline;
   it cannot say whether the opening price was fair. A part bought badly in 2023 and eroded
   perfectly since looks healthy here. Answering that needs a should-cost build-up from materials,
   process time and overhead — a different exercise with different inputs.

2. **The erosion benchmark is an assumption, and the most contestable input in the project.** It
   lives in `Ref_PriceErosionBenchmark` with a `SourceNote` on every row precisely so a category
   manager can challenge it. Every figure in the case study moves if those rates move.

3. **Reject attribution is coarse.** `Ref_RejectReason` splits causes into Supplier, Lumen and
   Shared, but "Shared" covers both contamination and transit damage, which have different owners
   in practice.

4. **No supplier financial or geographic risk.** Concentration is measured by spend share only.
   Single-site exposure, financial health and geopolitical risk are not in this model, and a
   "supplier risk score" built from delivery and quality alone would be named for something it
   does not measure.

5. **Leverage weights are judgement.** The 40/20/30/10 split across alternatives, requalification
   time, revenue share and contract status is stated explicitly in both the SQL and the DAX so it
   can be argued with — but it is a judgement, not a measurement.

advisory.
