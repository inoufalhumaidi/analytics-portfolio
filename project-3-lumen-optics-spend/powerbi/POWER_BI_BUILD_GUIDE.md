# Power BI build guide — Lumen Optics Spend Scorecard

**Written for:** an analyst rebuilding this report from scratch against their own SQL Server.

> **Data disclosure.** Lumen Optics Manufacturing is a fictional photonics manufacturer. All data
> is synthetic and generated by the scripts in `sql/`. No confidential data is used and no claim is
> made about any production system.

---

## What is scripted and what is not

| Layer | How it is built | Why |
|---|---|---|
| Tables, columns, relationships, hierarchy | `Build_PowerBI_Model.ps1` | Reviewable, diffable, rebuildable |
| 69 DAX measures | `Build_PowerBI_Model.ps1` | So the leverage weights in DAX can be checked against the weights in SQL |
| Report pages and visuals | **By hand, following §4 below** | There is no supported scripting path for the report layer |
| Verification | `Validate_PowerBI_Model.ps1` | Structural checks pass on an empty model; only querying it proves anything |

The scripts talk to the local Analysis Services engine that Power BI Desktop exposes while a file
is open — the same mechanism Tabular Editor and DAX Studio use. There is no CLI for this.

---

## 1. Build the model

1. Run the SQL in order (`sql/01` … `sql/07`); expect **21/21** on the UAT suite.
2. Open **Power BI Desktop** on a blank report and leave it open.
3. `powershell powerbi/Build_PowerBI_Model.ps1`

On first run it downloads the official Microsoft AMO client package from nuget.org into
`.amo_libs/` (~6 MB, gitignored).

**The first refresh raises a credential prompt inside Desktop.** The script will appear to hang
until you click through it — choose Windows / Integrated authentication and any privacy level.
This happens once per Desktop session, and again after the tables are dropped and recreated.

4. Save the file as `powerbi/Lumen_Spend_Scorecard.pbix`.

## 2. Verify it before building anything on top of it

```
powershell powerbi/Validate_PowerBI_Model.ps1
```

Expect **31 of 31 checks reconcile**. This queries the model in DAX and compares each answer with
the SQL that is supposed to produce it, to the number of decimals SQL publishes.

Do not skip this and do not substitute a glance at the field list. `Build_PowerBI_Model.ps1` will
report complete success against a model that loaded zero rows — creating tables, relationships and
measures never touches the data, and a Desktop refresh does not even populate `EstimatedRowCount`.

One caveat worth stating plainly: this proves Power BI and SQL **agree**. It does not prove either
is right. Project 1 in this portfolio shipped an Excel workbook and a SQL view that agreed with
each other exactly and were both wrong, because both were derived from the same flawed written
definition. Agreement is necessary, not sufficient.

## 3. The model

**Nine tables.** Four dimensions (`Dim_Date`, `Dim_Vendor`, `Dim_Part`, `Dim_Buyer`), three facts
loaded from SQL views (`POLine`, `PriceErosion`, `RenegotiationQueue`) and two reference tables
(`Ref_SpendTargets`, `Ref_PriceErosionBenchmark`), plus `Ref_Reporting`.

The facts come from the **views**, not the raw tables. The landed-cost identity, the dated contract
resolution and the erosion model are each defined once in SQL and asserted by the acceptance tests;
re-deriving them in DAX would create a second definition free to drift from the first. DAX does the
aggregation, the ratios, the time intelligence and the conditional formatting — what a semantic
model is actually for.

**Ten relationships**, all single-direction, all many-to-one onto a dimension. `Dim_Part` and
`Dim_Vendor` each feed three facts, which is an ordinary star; the ambiguity trap would be a
relationship *between* two facts, and there is none.

**`Ref_Reporting`** holds one row — the as-of date and the start of the trailing twelve months,
read straight out of `fn_SpendKPI`. Every TTM measure takes its window from it, so the model and
the SQL scorecard cannot drift apart. Anchoring on `MAX(POLine[OrderDate])` instead looks identical
today, because the last order happens to fall on the as-of date, and would silently widen the
window the moment it did not.

### Measure groups

| Folder | Contains |
|---|---|
| `00 Reporting` | `As Of Date`, `TTM Start` |
| `01 Spend` | Extended price, landed cost, freight, expedite, line and quantity counts |
| `02 Contract` | On-contract and maverick spend, PPV, ambiguous-contract line count |
| `03 Erosion` | Spend-weighted capture %, annual opportunity, value already ahead of curve |
| `04 Quality` | Acceptance, rejected value, cost per accepted unit, cost index, duplicate spend |
| `05 Delivery` | On-time %, average days late, expedite share |
| `06 Leverage` | Single-source share, top-5 concentration, leverage score |
| `07 Queue` | Queue opportunity, this-quarter pairs and coverage |
| `08 Status` | RAG colour and status measures |
| `09 TTM Scorecard` | The headline KPIs pinned to the published window |

### Three decisions worth understanding before you edit a measure

**Base ratios respond to filters; the TTM variants pin the date.** `[Maverick Spend %]` answers
over whatever the user has sliced, which is what makes a trend line or a per-vendor breakdown mean
anything. But the published scorecard is a trailing-twelve-month figure, and a card with no slicer
would show an all-history number that looks equally plausible and is not the number in the case
study. So the headline KPIs have an explicit `(TTM)` twin, and those are what the scorecard cards
bind to. Nobody has to remember to set a slicer for the page to be right.

**RAG colours bind to the TTM variants.** `DATESBETWEEN` replaces only the *date* filter, so a
status measure still answers "how is this vendor doing" when a vendor is selected — it just refuses
to answer it over a window other than the published one. Colouring an all-history figure against a
TTM target is a red light with no meaning.

**A colour measure returns a hex string, not a number.** Power BI's "format by field value" expects
a colour. Returning `1`/`2`/`3` and hoping the rule interprets it is the commonest reason a
conditional-format rule silently does nothing — this project hit exactly that in Project 1.

**`Erosion Capture %` and `Annual Opportunity` have no TTM twin, deliberately.** The erosion model
already weights by TTM spend internally and spans each pair's whole price history by design.
Windowing it again would double-apply the window and shorten the very history the trend measures.

background via **Format by field value**:

|---|---|---|
| Direct-materials spend | `Spend (TTM)` | — |

| Annual opportunity | `Annual Opportunity` | — |
| Maverick spend | `Maverick Spend % (TTM)` | `Maverick Spend Colour` |
| Purchase price variance | `PPV % (TTM)` | `PPV Colour` |

| On-time delivery | `On Time Delivery % (TTM)` | `On Time Delivery Colour` |
| Single-source spend | `Single Source Spend % (TTM)` | `Single Source Colour` |

Below them, a line chart of `Extended Price` by `Dim_Date[Calendar]` (Month level), and a bar chart
of `Extended Price` by `Dim_Part[Category]`.

**Put the point of the project on this page in text:** purchase price variance is green while
erosion capture is red. The two cards sitting side by side is the argument.

### Page 2 — Erosion detail

- Table: `Dim_Part[PartNumber]`, `Dim_Vendor[VendorName]`, `FirstPrice`, `LastPrice`,
  `ExpectedPrice`, `ErosionCapturePct`, `AnnualOpportunity` from `PriceErosion`.
- Scatter: `ErosionCapturePct` (X) against `TTMSpend` (Y), one point per pair, sized by
  `AnnualOpportunity`, coloured by `Dim_Part[IsSingleSource]`. The sole-source cluster low on the
  X axis is the finding.
- Cards: `Pairs Assessed`, `Pairs Capturing Under 20%`, `Spend on Flat Pairs`.
- Slicers: `Dim_Part[Category]`, `Dim_Part[Criticality]`, `Dim_Vendor[VendorTier]`.

### Page 3 — Renegotiation queue

- Table from `RenegotiationQueue` sorted by `PriorityRank`: rank, part, vendor, buyer, `TTMSpend`,
  `AnnualOpportunity`, `LeverageScore`, `ActionCode`, `RecommendedAction`.
- Cards: `Queue Pairs`, `This Quarter Pairs`, `This Quarter Opportunity`, `Quarter Coverage %`.
- Slicer on `RenegotiationQueue[IsThisQuarter]` — default it to **True**, so the page opens on the
  work that is actually schedulable rather than on 185 rows nobody can action.

### Page 4 — Vendor quality

- Table: vendor, `Qty Received`, `Qty Accepted`, `Acceptance Rate %`, `Rejected Value`,
  `Cost per Accepted Unit`, `Cost Index vs Best`.
- Filter `Dim_Part[PartNumber]` to a shared part (LOM-0072 is the worked example) to show the
  cheapest vendor by unit price being the dearest per *accepted* unit.

### Page 5 — Data quality

`Duplicate PO Lines`, `Duplicate PO Spend`, `Ambiguous Contract Lines`, and a note that the gate
passes at 0.497% against a 0.500% tolerance — by three thousandths of a percentage point, which is
luck rather than comfort.

## 5. Re-running

`Build_PowerBI_Model.ps1` is idempotent: it clears relationships first, then drops and recreates
every table and measure.

The order matters and is not obvious. Removing a table does **not** cascade to the relationships
that reference it — TOM leaves them dangling and then refuses the save with
`Relationship 'Relationship' points to deleted table 'Dim_Date'`. That error only ever appears on a
re-run, never on a first run, which is exactly the kind of thing a script gets shipped without.

Two smaller traps in the same area: `RelationshipCollection` exposes `Remove(object)` and not
`RemoveAt(index)`, and PowerShell's fallback for a missing method is to enumerate the collection
and try the method on each *member* — so `RemoveAt` fails with a message naming
`SingleColumnRelationship` rather than the collection. And the collection must be snapshotted with
`@()` before removing from it.
